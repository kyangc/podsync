## 已确认的因果链

12:08 再查，恢复器虽为 ready，观察事故已从早晨的 18 条增至 31 条。
先前有限重验修正了永久阻塞的状态机行为，但没有移除反复启动宿主管理进程的延迟来源。

- 现场捕捉两次 961.963/975.052 ms 的 inspect：宿主 Python 启动分别占
  904.447/885.677 ms，守卫约 2 ms，Docker CLI 为 55.129/85.899 ms。
  同窗没有 suspend 或 wall-clock step；延迟可定位到宿主解释器启动/调度阶段。
- 旧超时处理只杀 wrapper。真实合成子进程复现证明，其 Docker 后代可在超时后继续存活；
  修复为守卫后 exec、整组取消与回收，继承输出管道也受同一总期限约束。
- 原身份检查把 diskutil 观察失败混同介质身份不符，可能进入 drain/重连。
  新观察器区分“未知”与成功观察到不同身份，真实 UUID/路径变化仍停止准入。
- 本地 SSH 超时不能证明远端 writer 已停止。隔离 guest 的 barrier 用例复现了迟到写入；
  新协议固定原到期点，并要求完整回执后的宿主 nonce 确认，未知结果不能签发确认。
- 旧门禁只在读取 NFS proof 前核期限。同一 Linux FIFO 用例中，旧 gate 约 2.237 秒后
  放行已过期租约；新 gate 在约 2.070 秒按原两秒预算拒绝。

宿主当时 swap 用量约 10.6 GiB、内存 16 GiB，但这不足以把历史十秒 inspect 或两秒发布
唯一归因到换页、CPU 队列或其他内核等待。后续宿主管理进程长等待附近，guest 本地 Docker API
仍以毫秒级返回；部分栈采样没有有效调用栈，不能声称已找到具体内核等待。
平台另一个任务修复的双重校时及代理问题，也不能无调用证据直接套成本次原因。

## 修复与保留边界

固定登记 ID 的暖驻只读观察器每次重新执行原守卫、核完整容器指纹、restart policy 和原 StartedAt，
不提供任意命令 RPC。第一步移除每轮 Python 启动后，30 次交错 inspect 中位从 56.42 ms 降至 18.88 ms，
但 13:12 又遇内部 Docker CLI 超时。因此最终在原 wrapper 守卫内只 GET 固定 ID，
每轮完整观察新建/关闭 Unix 连接，防止路径重绑定后继续读取旧 Engine；输出合计最多 2 MiB，
非 200、坏 JSON 或上下文漂移都失败关闭。60 次最终候选的生产只读指纹对照全部通过，
中位 10.05 ms、最大 65.07 ms；普通 Docker 控制仍使用原 CLI。
身份观察也暖驻隔离，每轮实际执行 diskutil 和路径检查，不缓存 true；中位约 107.21 ms，
原逐次启动约 404 ms。每个请求、输出大小及后代清理均有界，观察仍限三秒。
创建、接收与解码后重新核 continuous deadline；宿主暂停后的排队迟到响应、通用命令的迟到成功
均由确定性 clock 跃进回归覆盖，不能作为准时成功。

v2 租约由 Linux 同一会话先提供 wall/boottime/boot ID，两个到期点都固定为原时点 +10 秒。
guest 写入、fsync、replace、回读成功且 SSH 在原两秒内完成后，宿主才写绑定完整租约的
`ack-<nonce>`。迟到 writer 不能重新计算 now+10，未知写入没有确认凭据。
Podsync 的 v2-only gate 核完整确认、代次证明和 Linux 双时钟，在可能阻塞的读取及程序查找后
再次检查期限；两秒总读取期限同时核 CLOCK_BOOTTIME，计入 Linux suspend。只有确认文件尚未出现时，才在同一原两秒总预算内重新读取。

只读 inspect、身份未知和已确认慢发布共用原三次连续观察上限，一/三秒退避；
成功恢复前重新验证原会话、制品、介质与 I/O。持续三次不可用、未知业务写入、真实身份漂移
或新会话首次准入失败仍拒绝并保留结果。SIGTERM 后不启动新传输、确认或消费者。
没有扩大连接预算、TTL、SSH 时限或门禁预算。
