## 已证实的失败边界

11:06—11:11 刷新现场后，今早的超时仍可复现，而且 NAS 也出现同类失败，不能只归因于本机网络。

| 对照 | 结果 |

| HTTP/1.1、HTTP/2、两个公开 IPv4 地址 | 均可复现；单次请求指定真实地址也未消除故障，没有修改系统 DNS |
| 同一媒体域的 Cloudflare 边缘直返接口 | 两处均 200，首字节约 0.27 / 0.52 秒；本机与 NAS 分别到达 NRT / LAX |
| Worker 公开健康、RSS、D1 | 健康 200；三个样本 RSS 均包含对应 enclosure，长度与 D1 一致；后台事件持续更新 |
| nginx 内部健康、直接 Range | 健康立即 204；三个既有文件均有源站 206 / 1024 字节记录 |
| connector | 实际参数仍为 HTTP/2；`/ready` 200、有效连接 4、历史累计请求错误 4，近三小时没有连接告警；同时存在 10 个长期未完成请求 |

connector 的实际 TCP 7844 目标是**真实 IP**。只读查阅网络项目已实施记录及共享控制器后，确认此前的 Tunnel DNS 例外已上线，当前四条连接经过同一条通用代理链。本次不能沿用 10 月 19 日“旧 Fake-IP 映射失效”的根因。

传输状态进一步显示：nginx 到 connector 的多个连接积压媒体数据；一条 connector 到边缘的 TCP 连接存在约数百 KB 发送队列。只读 goroutine 快照中，媒体处理协程等待 HTTP/2 数据写入，底层写协程等待 TLS/socket 写出。路由器对应流量计数仍在增加，说明连接缓慢推进，不能称为完全断线。

这些证据把本次故障收敛到 **connector 向边缘传输响应时的阻塞/背压**。具体是共享代理链吞吐、到边缘的路径还是连接调度导致，尚未通过隔离对照证明；本机 TUN 的存在也不能单独建立因果关系。

## 已实施的最小缓解

11:11—11:12 仅重启 Podsync 专属 `media-tunnel` 一次，刷新传输连接。重启前保留现场证据；镜像和命令逐项比较一致，继续使用 HTTP/2。Podsync/nginx 的启动时间与重启计数保持不变。

该操作会中断隧道在途请求。停止/重新注册期间出现退出日志及一次“已连接同一服务器”的注册重试，之后四条连接注册完成。重启后请求错误计数从新进程的 0 开始，不能把计数清零本身视为恢复证据。

没有更改共享路由器、代理选择、DNS、Worker、Access、媒体、D1 或 Badger，没有触发同步、补数据、清缓存、升级镜像或部署配置。

| 前一天 22:25，历史下载失败后已发布样本 | 两处均 206 / 1024 字节 / MISS | 两条 200 记录，均为 28,643,873 字节，与 D1 一致 |

六次 MISS 都按唯一查询值找到 nginx 记录，构成真实回源证据。随后重复这些地址均为 HIT / 206 / 1024 字节，三个样本的本机/NAS 内容摘要分别一致。

唯一查询会让 Cloudflare 回源拉取**完整对象**，即使客户端 Range 只读取 1KB。本次六次成功探测的完整回源持续数分钟；填充期间公开健康首字节约 6—11 秒，不能把早期 206 当作完全恢复。停止新增唯一查询、等待既有传输完成后，11:18 观察到在途请求为 0；健康恢复 204 / no-store，首字节约 0.8—1.1 秒。

11:19 再读 RSS 原始媒体地址，三个样本从两处均为 206 / 1024 字节，首字节约 0.46—2.44 秒。11:21 公开媒体健康从两处均为 204 / no-store，首字节约 0.72—0.77 秒；有效连接 4、在途请求 0、重启后请求错误 0，近五分钟无连接告警。后台最新事件为 11:21:50，重启后的 warn/error 为 0；Dashboard 未认证请求仍 302 到 Access。

本次完成连接刷新与短期外部读取恢复验证，**尚未证明共享出口下并发回源的长期稳定性**。下次复发应先保留传输队列、流量增量、在途请求与健康延迟，再评审仅针对该 connector 的出口隔离对照。共享节点组、全 NAS 路由或系统 DNS 的修改需要另行明确授权；不要循环重启来代替取证。

## 管理 HEAD 的独立验收缺口：本地修复待部署

管理检查在公开读取恢复后仍间歇返回 502，响应明确为上游 405；同一批三个文件在 NAS 内部的认证 HEAD 始终 204。成功与失败并非固定对应某个文件。connector 的 405 计数与失败检查对应，说明这类响应来自隧道后的处理，而非公开媒体缺失。

Worker 的管理请求构造器原先没有指定缓存模式。管理 URL 仍以 `.mp3` 结尾；[Cloudflare 文档](https://developers.cloudflare.com/cache/concepts/cache-behavior/)明确说明，可缓存 HEAD 的冷缓存请求会改用 GET 回源，源站生命周期接口只支持 HEAD/DELETE。现场与此机制吻合，但本次 OAuth 权限无法读取区域缓存规则（只读请求返回 403），没有把某条具体规则认定为已证实根因。

本地为管理请求增加 `cache: "no-store"`，使用[官方支持的子请求缓存绕过](https://developers.cloudflare.com/changelog/post/2024-11-11-cache-no-store/)保留请求方法并读取当前对象状态。回归测试模拟冷缓存 HEAD→GET 边界：修改前返回 502，修改后保持 HEAD 并返回 204。该设置仅用于认证管理生命周期请求，公开媒体请求不经过此构造器。

本地验证通过：Worker typecheck、16 个测试文件 / 197 项测试、Wrangler dry-run 打包、`go fmt ./...`、`make test`、`git diff --check` 和本地 Markdown 链接检查。已有 golangci-lint 使用 Go 1.26 构建，与默认 Go 1.27 标准库不兼容；在该命令中指定匹配的 Go 1.26.4 工具链后，lint 通过、0 issues，未修改项目工具链配置。
